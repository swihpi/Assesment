# Customer context and value

Assume a sports organisation wants to combine customer profiles with other information for analytics and future audience decisions. Its source CRM remains authoritative. The available integration interface is a daily CSV report containing customer ID, name, region, joining date, last-purchase date and one simplified marketing-permission field. No usable CRM API or supported application-specific connector is available in the assumed environment; the CRM can schedule the export and deliver it to customer-controlled SFTP at 02:00 UTC.

The starting demonstration contains four dummy records: two are released and two need correction. A separate generated 10,000-record case verifies 9,200 released records and 800 deliberately missing customer IDs. Both use the same processor; the larger case is additional verification, while the small file makes individual decisions easy to inspect.

The report interface may change when an administrator edits a template: headings can be renamed, columns reordered, or an extra field introduced without changing the underlying database. The problem may be in the report rather than the CRM database: an export mapping can omit the ID, or a join to address history can repeat the same customer ID with different address values. An invalid date may come from a text field or an export transformation; it would not normally be stored as an impossible date in a proper date column. The source owner investigates the cause. An empty purchase date may be legitimate; missing identity prevents trusted linking; missing permission must not become assumed permission. These are hypothetical conditions used to make the processing decisions concrete.

The integration contract archives the received file, validates before database loading, and separates approved records from correction cases. The proposed raw-file location is OCI Object Storage; ADW receives classified readable records after validation. A proposed ADW destination supports record-level updates and unresolved exceptions: omission is not deletion and a partial file must not replace a complete table. For 10,000 fully readable records with 800 independent required-value failures, the intended outcome is 10,000 received records retained, 9,200 approved, and 800 visible correction cases. The local file-to-file demonstration proves that selection policy; ADW loading is proposed.

The CRM/data owner owns source correction, with integration engineering responsible for mappings and processing. Reports should be securely routed to the responsible owner, corrected at source and reprocessed with reconciliation. Missing permission remains UNKNOWN unless authoritative evidence resolves it. Daily CSV ingestion is insufficient to establish current permission at campaign activation time.

The wider sports context comes from Stefan's internal NHL sentiment initiative within Oracle. The wider ambition combined batch and streaming sources, preferably using OIC to automate data movement from source to target. Aggregate social sentiment might inform campaign timing, while customer profiles could support individual audience selection. The next step would have been to connect this information to tools that execute specific marketing campaigns. The processor implements neither sentiment scoring nor campaign execution, and aggregate sentiment does not establish an individual customer's sentiment. The demonstrated value is dependable, usable input and a recoverable correction path, rather than an unmeasured revenue claim.
